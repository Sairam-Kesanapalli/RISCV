01 Restoring Binary Division — the iteration loop
QI am unable to understand the S_DIV_ITER code block.

This implements restoring binary long division — one bit of quotient computed per clock cycle.

The big idea

The quotient register starts holding the dividend. Its bits are consumed one at a time as new quotient bits are written in from the right over WIDTH cycles.

Step 1 — Left shift + pull-in
shifted_rem = {remainder[WIDTH-1:0], quotient[WIDTH-1]};

1-bit left shift of remainder with the MSB of quotient (next dividend bit) shifted in at the bottom. Mirrors "bring down the next digit" in long division.

Step 2 — Trial subtraction
sub_result = shifted_rem - {1'b0, divisor_reg};

sub_result is WIDTH+1 bits wide. The extra MSB sub_result[WIDTH] is the borrow/sign flag — 0 = subtraction succeeded, 1 = went negative.

Step 3 — Restore or keep
sub_result[WIDTH]remainder getsquotient gets
0 (success)sub_resultshift in 1
1 (fail)shifted_rem restoredshift in 0
Step 4 — Loop control
count <= count + 1;
if (count == WIDTH - 1) state <= S_FINISH;

Runs exactly WIDTH iterations, one per bit, then transitions to S_FINISH.

Why "restoring"? Because when subtraction fails you restore the remainder back to what it was — unlike non-restoring division which applies a correction at the end.
02 Forwarding — what each block does
QExplain what the forwarding parts are doing according to the code.
The problem

The instruction in EX needs register values that instructions in MEM or WB haven't written back yet. Forwarding bypasses the register file and feeds the fresh value directly.

forwardA decision logic
// Priority 1 — value from MEM stage (newest)
if (ex_mem_RegWrite && (ex_mem_rd != 0) && (ex_mem_rd == id_ex_rs1))
    forwardA = 2'b10;

// Priority 2 — value from WB stage
else if (mem_wb_RegWrite && (mem_wb_rd != 0) && (mem_wb_rd == id_ex_rs1))
    forwardA = 2'b01;

// No hazard — use register file value
else
    forwardA = 2'b00;

Three conditions must all be true to forward: the stage is writing a register, it's not x0, and it's writing the register EX needs. forwardB is identical but checks id_ex_rs2.

The actual mux
assign forwarded_read_data1 =
    (forwardA == 2'b10) ? ex_mem_alu_result :  // from MEM stage
    (forwardA == 2'b01) ? wb_write_data     :  // from WB stage
                          id_ex_read_data1;   // register file
Why EX/MEM is checked before MEM/WB

If two back-to-back instructions both write the same register, EX/MEM has the newer value. The if/else if priority ensures the newest value always wins.

At C3: load_use_stall=1 fires. At C4: the bubble is in ID/EX — id_ex_MemRead=0. The stall condition is gone. Pipeline resumes automatically.

Hazard 1 — SUB at C4

ADD is in EX/MEM. ex_mem_RegWrite=1, ex_mem_rd=x1=id_ex_rs1 → forwardA=2'b10 → forwarded_read_data1 = ex_mem_alu_result. ✅

Hazard 2 — AND at C5

EX/MEM check fails (SUB's destination is x4, not x1). Falls through: mem_wb_RegWrite=1, mem_wb_rd=x1=id_ex_rs1 → forwardA=2'b01 → forwarded_read_data1 = wb_write_data. ✅

Both hazards fixed by forwarding alone. No stalls needed.

06 Is the cleaner ternary an optimization?
QWill rewriting the ternary without the duplicate become an optimization?

No — only a readability improvement. Both versions synthesize to the exact same 4-to-1 mux. The synthesizer sees the logic function and generates identical gates.

An actual optimization would require explicitly marking 2'b11 as a don't-care using casez or unique case, potentially letting the tool reduce it to a 3-to-1 mux. But for a 2-bit select on 32-bit data, the silicon difference is negligible.
07 Why is the mul/div stall block left empty?
QWhy is the stall region left incomplete / empty?
// ID/EX register
end else if (stall) begin
    // Multiplier stall: hold state stable
    // ← no assignments = implicit hold = registers freeze
end

In a clocked always @(posedge clk) block, writing no assignment means the register holds its current value. That is exactly what you want — freeze the mul/div instruction in ID/EX while it finishes computing.

Compare this to load-use stall which explicitly zeroes everything (injecting a bubble). Mul/div stall does the opposite — it preserves the instruction in place.

09 Each hazard explained in detail
QExplain about each hazard and how they got fixed.
1. RAW — Back-to-back ALU

At C4, ADD is in EX/MEM and SUB needs x1 in EX. ex_mem_RegWrite=1, ex_mem_rd==id_ex_rs1 → forwardA=2'b10. ADD's result bypassed directly from EX/MEM register.

2. RAW — Two instructions apart

At C5, ADD is in MEM/WB and AND needs x1 in EX. EX/MEM check fails (different rd). MEM/WB check fires → forwardA=2'b01 → value from wb_write_data.

3. Load-use hazard

Forwarding can't help — the memory data isn't available until end of MEM. Fix: stall 1 cycle (freeze IF/ID, inject bubble into ID/EX). Next cycle, loaded value forwards from MEM/WB.

4. Control hazard — Branch/Jump

Branch resolves in EX at cycle 3. Two wrong instructions are in IF and ID. take_branch_or_jump=1 → flush=1 → both IF/ID and ID/EX replaced with NOPs. PC loaded with id_ex_pc + id_ex_imm. Cost: 2 wasted cycles per taken branch.

5. Structural — MUL/DIV multi-cycle

While done=0: pipeline frozen, bubbles injected into EX/MEM each cycle. ex_stage_md_active ensures start pulses only once. When done=1, stall=0 and the result is latched into EX/MEM.

6. WAR / WAW — don't exist here

In an in-order pipeline, no instruction can overtake another. You can never write before an earlier instruction reads (WAR) or write before an earlier instruction writes (WAW).

10 What is flush and why is it used?
QWhat is this flush? Why is it used?

The pipeline doesn't wait. By the time BEQ resolves in EX (cycle 3), two instructions from the wrong path are already inside the pipeline:

0x00:  BEQ x1, x2, 0x40   ← branch to 0x40
0x04:  ADD ...             ← fetched speculatively (WRONG)
0x08:  SUB ...             ← fetched speculatively (WRONG)
...
0x40:  AND ...             ← actual next instruction

Flush replaces those two wrong instructions with NOPs before they modify registers or memory.

Why NOP specifically?

Zeroing control signals is enough for ID/EX (no writes happen), but for IF/ID you need a valid instruction encoding. 32'h00000013 = addi x0, x0, 0 — architecturally guaranteed to do nothing.

Flush = overwrite wrong instructions with NOPs before they reach a stage that has side effects (EX writes registers, MEM writes memory).
11 In-order vs Out-of-order pipelining
QWhat is in-order pipelining and out-of-order pipelining?
In-Order

Instructions enter, execute, and complete in the exact order they appear in the program. No instruction can overtake another. Your RV32IM processor is in-order.

The problem with in-order

If one instruction is slow (e.g. a load), all instructions behind it must stall — even if they have no dependency on it.

Out-of-Order

The processor looks ahead at multiple instructions and executes whichever one is ready, regardless of program order. A Reorder Buffer (ROB) holds results and commits them in-order at the end so the programmer never sees wrong behaviour.

PropertyIn-OrderOut-of-Order
Execution orderStrict program orderAny ready instruction
Hazards to handleRAW onlyRAW + WAR + WAW
ComplexitySimpleVery complex
PerformanceLowerHigher
ExamplesYour RV32IM, ARM Cortex-MIntel Core, AMD Ryzen, Apple M-series
WAR and WAW hazards don't exist in your processor because it is in-order. They only appear in out-of-order designs where instructions can overtake each other.
12 load_use_stall — is rs1/rs2 really from the next instruction?
QBoth are id_ex — how can you say (id_ex_rd == rs1) is a "next instruction" check?

Sharp observation. rs1 and rs2 are not from the ID/EX register. They are declared as plain wires sliced from if_id_instr:

// In ID stage — from IF/ID register (one stage BEHIND ID/EX)
assign rs1 = if_id_instr[19:15];
assign rs2 = if_id_instr[24:20];
SignalStageMeaning
id_ex_rdEX stageDestination of the load instruction
rs1, rs2ID stageSources of the instruction behind it

The stall check is correctly asking: "does the load in EX write to a register that the instruction currently in ID wants to read?"

If it had used id_ex_rs1/id_ex_rs2 instead, it would be comparing EX against EX — the same instruction against itself, which is meaningless.
13 Why flush and stall are not applied to EX/MEM and MEM/WB
QWhy are pipeline_stall and flush cases not used at ex_mem and mem_wb registers?
Load-use stall

The hazard is detected when LW is in EX and ADD is in ID. The instructions that need to freeze are behind the load — in IF and ID. EX/MEM and MEM/WB are ahead — already past the problem and must keep moving to complete normally.

Branch/jump flush

Branch resolves in EX. Wrong instructions are in IF and ID. EX/MEM and MEM/WB contain instructions fetched before the branch — they are correct and must complete.

Mul/div stall

EX/MEM gets a partial bubble (RegWrite/MemRead/MemWrite zeroed) to prevent side effects. MEM/WB is left alone — it holds a correctly computed instruction that must write back.

IF/IDFrozenNOPFrozen
ID/EXBubbleNOPHeld stable
EX/MEMNormalNormalPartial bubble
MEM/WBNormalNormalNormal
Core rule: Only touch the registers that contain wrong or premature instructions. Everything ahead of the hazard is correct and must be left alone.
