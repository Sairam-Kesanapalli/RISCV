Q1 Why are Branch and Jump listed under MEM signals, not EX? ▾
// the design choice

The guide classifies signals by where they are consumed, not where they are generated. In the textbook Patterson & Hennessy pipeline, the branch decision is resolved in the MEM stage, not EX.

EX stage: computes ALU result + zero flag MEM stage: evaluates (Branch & zero) → triggers PC flush

So Branch and Jump must travel through the EX/MEM register before being acted upon — hence they're grouped with MEM signals.

// better approach — resolve in EX

Use a dedicated comparator in EX instead of the main ALU:

// EX stage — dedicated branch comparator
wire branch_taken = id_ex_Branch & (id_ex_read_data1 == id_ex_read_data2); // BEQ
Resolution StageStages FlushedSignal Category
MEM (textbook)2 (IF, ID)MEM signal
EX (optimized)1 (IF)EX signal
Q2 How do I implement Step 1 — the combinational control unit? ▾
// what you're replacing

The multi-cycle control unit is sequential — it drives different signals based on FSM state. Delete the FSM entirely and replace with a purely combinational always @(*) block.

// the new control unit
module control_unit (
    input  [6:0] opcode,
    // EX signals
    output reg [2:0] ALU_OP,
    output reg       ALUSrcA, ALUSrcB,
    // MEM signals
    output reg       MemRead, MemWrite, Branch, Jump,
    // WB signals
    output reg       MemToReg, RegWrite
);

always @(*) begin
    // Defaults — CRITICAL, prevents latches
    ALU_OP=3'b0; ALUSrcA=0; ALUSrcB=0;
    MemRead=0; MemWrite=0; Branch=0; Jump=0;
    MemToReg=0; RegWrite=0;

    case (opcode)
        7'b0110011: begin // R-type
            ALU_OP=3'b010; RegWrite=1;
        end
        7'b0010011: begin // I-type ALU
            ALU_OP=3'b011; ALUSrcB=1; RegWrite=1;
        end
        7'b0000011: begin // Load
            ALU_OP=3'b000; ALUSrcB=1;
            MemRead=1; MemToReg=1; RegWrite=1;
        end
        7'b0100011: begin // Store
            ALU_OP=3'b000; ALUSrcB=1; MemWrite=1;
        end
        7'b1100011: begin // Branch
            ALU_OP=3'b001; Branch=1;
        end
        7'b1101111: begin // JAL
            ALUSrcA=1; ALUSrcB=1; Jump=1; RegWrite=1;
        end
        // ... etc
    endcase
end
endmodule
Key rule: Always set defaults first. Any unhandled opcode otherwise leaves signals undefined — causing X-propagation in simulation or latches in synthesis.
// two-level decode

The main control unit only looks at opcode. A separate ALU control submodule in EX uses funct3/funct7 to pick the exact ALU operation (ADD vs SUB vs AND etc.). This keeps the main control unit clean.

Q3 Pipeline registers look odd (IF/ID, ID/EX…). How can they store data from 2 different cycles? ▾
// the name means location, not contents

IF/ID does not mean "stores IF data AND ID data simultaneously." It means the register sitting on the boundary between IF and ID — a handoff box between two workers on an assembly line.

IF stage │ [IF/ID] │ ID stage │ [ID/EX] │ EX stage │ holds │ reads │ holds │ │ IF output│ from it │ ID output│
// concrete example — ADD x1,x2,x3
Cycle 1 → IF fetches instr: IF/ID ← { pc=0x1000, instr=ADD } Cycle 2 → ID decodes it: ID/EX ← { rd=x1, rs1=x2, RegWrite=1 ... } IF/ID ← { pc=0x1004, instr=NEXT } Cycle 3 → EX computes: EX/MEM ← { alu_result=... }
// they are just wide registers
// IF/ID = 64-bit register with a meaningful name
always @(posedge clk) begin
    if_id_pc    <= PC;        // 32 bits
    if_id_instr <= mem_instr; // 32 bits
end

// ID/EX = ~200-bit register
always @(posedge clk) begin
    id_ex_pc         <= if_id_pc;
    id_ex_read_data1 <= reg_rs1;
    id_ex_rd         <= rd;
    id_ex_RegWrite   <= RegWrite;
    // ...
end
Mental model: Each stage takes a photograph of everything it computed, puts it in the register. The next stage reads that photograph next cycle. The register name just says between which two stages the photograph lives.
Q4 Do all the IF, ID, EX… blocks become sequential in pipelining? ▾
// no — stages stay combinational

The stages themselves stay combinational. Only the pipeline registers between them are sequential.

IF logic → combinational (reads imem with PC) [IF/ID] → sequential (posedge clk snapshot) ID logic → combinational (decodes, reads regfile) [ID/EX] → sequential (posedge clk snapshot) EX logic → combinational (ALU computes) [EX/MEM] → sequential (posedge clk snapshot) MEM logic → combinational (reads/writes dmem) [MEM/WB] → sequential (posedge clk snapshot) WB logic → combinational (mux → writes regfile)

always @(posedge clk) appears only in the 4 pipeline registers and the PC update. Everything else is assign or always @(*).

// separate modules or one file?

Both are valid. One file is fine for a personal project. The important thing is logical separation in the code, not physical file separation. Structure the file with clear comments marking each stage and each pipeline register block.

Delete from your current file: The multi-cycle state registers IR, MDR, A, B, ALUOut and the FSM inside control_unit.v. Replace the single state-update always block with 4 pipeline register blocks.
Q5 Before ID/EX captures instr1's PC, will instr2 overwrite IF/ID first? ▾
// no — both happen atomically at the same clock edge
posedge clk (cycle 2) │ ┌───────────┴───────────┐ ▼ ▼ IF/ID ← instr2 ID/EX ← old IF/ID value (overwrites instr1) (instr1's pc=0x1000 ✓)
// why non-blocking assignment guarantees this

The <= operator evaluates all right-hand sides before any left-hand side updates. So id_ex_pc <= if_id_pc reads the old value of if_id_pc, not the new one being written in the same cycle.

always @(posedge clk) begin
    // Both in the same always block — safe!
    if_id_pc  <= PC;          // PC = 0x1004 (instr2)
    if_id_instr <= mem_instr; // instr2

    id_ex_pc  <= if_id_pc;    // reads OLD if_id_pc = 0x1000 ✓
end
// full timeline
End of Cycle 1: IF/ID ← { pc=0x1000, instr=instr1 } End of Cycle 2: ID/EX ← { pc=0x1000 } ← reads OLD IF/ID ✓ IF/ID ← { pc=0x1004, instr=instr2 } End of Cycle 3: EX/MEM ← instr1 result computed ID/EX ← instr2 decoded

This atomic snapshotting is the entire reason pipelines work.

Q6 You said register file write port should be driven by WB — does that mean my code is wrong? ▾
// the module is instantiated once, used by two stages

The register file is instantiated once in the file but its ports are connected to two different stages simultaneously:

register_file rf (
    // READ ports — driven by ID stage
    .rs1(rs1), .rs2(rs2),
    .read_data1(read_data1),
    .read_data2(read_data2),

    // WRITE ports — driven by WB stage
    .reg_write(mem_wb_RegWrite),  // NOT RegWrite from control_unit
    .rd(mem_wb_rd),               // NOT rd from if_id_instr
    .write_data(wb_write_data)
);
// what's wrong in your current code
// WRONG — current connections
.reg_write(RegWrite),  // ← from control_unit (ID stage)
.rd(rd),               // ← from if_id_instr (ID stage)

// CORRECT
.reg_write(mem_wb_RegWrite),
.rd(mem_wb_rd),
Why it's a bug: When instruction A is in WB and instruction D is in ID simultaneously, using rd from ID means A writes its result into D's destination register. In multi-cycle this was fine because only one instruction existed at a time.
Q7 rd and RegWrite appear in ID/EX register. Aren't they used by the register file directly? ▾
// they travel through all registers but are only used at WB

They are captured in ID/EX not to be used there, but because they need to travel forward stage by stage — like a parcel on a conveyor belt, opened only at the last stop.

ID stage EX stage MEM stage WB stage generates → id_ex_rd → ex_mem_rd → mem_wb_rd rd, RegWrite id_ex_RW ex_mem_RW mem_wb_RW │ ▼ register_file write port
// ID/EX — carry forward only
id_ex_rd       <= rd;
id_ex_RegWrite <= RegWrite;

// EX/MEM — still carrying
ex_mem_rd       <= id_ex_rd;
ex_mem_RegWrite <= id_ex_RegWrite;

// MEM/WB — still carrying
mem_wb_rd       <= ex_mem_rd;
mem_wb_RegWrite <= ex_mem_RegWrite;

// WB — FINALLY used here
register_file rf(.rd(mem_wb_rd), .reg_write(mem_wb_RegWrite), ...);

Q9 What's the difference between shift-iterative multiply and Verilog's * operator? Why is iterative better? ▾
// what * actually synthesizes

When you write assign result = a * b, the synthesizer builds a combinational multiplier — a massive blob of adders and AND gates that computes in a single clock cycle. The problem:

32x32 combinational multiply: → ~1000+ logic gates → critical path delay: ~10-15ns → clock period MUST be ≥ 15ns → max frequency: ~66 MHz → EVERY instruction runs at 66 MHz because of this one op
// shift-and-add iterative method

Instead of computing all 32 bits at once, compute 1 bit per cycle:

always @(posedge clk) begin
    if (start) begin
        accumulator  <= 0;
        multiplicand <= A;
        multiplier   <= B;
        count        <= 0;
    end else if (!done) begin
        if (multiplier[0])
            accumulator <= accumulator + multiplicand;
        multiplicand <= multiplicand << 1;
        multiplier   <= multiplier   >> 1;
        count        <= count + 1;
    end
end
assign done   = (count == 32);
assign result = accumulator;

Each cycle does only: one add + two shifts — very few gates, very fast clock path.

Combinational *Iterative shift
Latency1 cycle32 cycles
Hardware cost~1000 gates~100 gates
Clock frequencyLow (bottleneck)High
Pipeline impactSlows everythingStalls only on MUL
Why iterative wins: MUL/DIV is ~5% of typical code. Keep your clock fast for the 95% common case. Accept 32-cycle stall for the rare case. This is why mul_div has busy, done, start signals — pipeline stalls (holds IF/ID, ID/EX, freezes PC) until done=1.
Q10 How does write-before-read in the register file fix the WB→ID RAW hazard? ▾
// the hazard being fixed

This only fixes the WB→ID hazard — the last possible RAW hazard:

Cycle 5: instr1 in WB — writing x1 = 42 Cycle 5: instr4 in ID — reading x1 Without forwarding: reads stale regs[x1] With forwarding: reads 42 directly
// the code
assign read_data1 =
    (rs1 == 0)             ? 0          :  // x0 hardwired zero
    (rs1 == rd && reg_write) ? write_data :  // forward from WB
                               regs[rs1];    // normal read

Both the read (ID stage) and write (WB stage) happen in the same cycle. The conflict is detected by rs1 == rd && reg_write and bypassed directly to write_data.

// what it does NOT fix
Hazard typeGapFixed by
EX/MEM → EX1 instrForwarding unit (future)
MEM/WB → EX2 instrForwarding unit (future)
WB → ID3 instrThis register file code ✓
Why x0 check comes first: x0 is hardwired to zero in RISC-V. Even if some instruction tries to write x0 (ISA ignores it), you must never forward that garbage value. The rs1 == 0 check short-circuits everything else.
Q11 What is a branch predictor? ▾
// the problem

By the time EX decides "branch taken", you've already fetched 2 wrong instructions into IF and ID:

Cycle 1: BEQ in IF Cycle 2: BEQ in ID, instr+4 in IF ← fetched blindly Cycle 3: BEQ in EX, instr+4 in ID, instr+8 in IF ↑ decision here if taken → instr+4 and instr+8 WRONG → flush → 2 wasted cycles
// types of predictors

Static (no hardware):

  • Always predict not taken — keep fetching PC+4
  • Always predict taken — always fetch target
  • BTFNT — backward branches taken, forward not taken (good for loops)

Dynamic (learns from runtime):

  • 1-bit predictor — remembers last outcome. Wrong on loop exits.
  • 2-bit saturating counter — needs 2 consecutive mispredictions to flip. Baseline for real CPUs.
  • Correlating predictor — looks at other branch outcomes too.
  • Tournament predictor — runs two predictors, selector learns which is better per branch. Used in modern CPUs.
// for your RV32I pipeline
// Simplest: predict always not taken
// On mispredict, flush IF and ID, redirect PC

wire mispredict = ex_mem_Branch & ex_mem_zero; // BEQ example

always @(posedge clk) begin
    if (mispredict) begin
        if_id_instr    <= 32'h00000013; // NOP
        id_ex_RegWrite <= 0;
        id_ex_MemWrite <= 0;            // squash wrong instrs
    end
end

assign PC_next = mispredict ? ex_mem_target : PC_plus_4;
Zero extra hardware beyond what you already need. Penalty only on taken branches. Modern CPUs achieve 95%+ accuracy with tournament predictors — branch penalty almost never happens in practice.
