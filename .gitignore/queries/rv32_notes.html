Q 01
Explain the original combinational mul_div module — what does each part do?

Interface

start is pulsed by the CPU to begin an operation. md_op is the 3-bit funct3 field from the instruction that selects which of the 8 operations to perform. A and B are the operands (rs1, rs2). Result is the 32-bit output — always the lower or upper half depending on the operation. busy and done are handshake signals back to the pipeline.

Operations — matching RISC-V spec funct3 encoding

Opfunct3Description
MUL000Lower 32 bits of signed×signed
MULH001Upper 32 bits of signed×signed
MULHSU010Upper 32 bits of signed×unsigned
MULHU011Upper 32 bits of unsigned×unsigned
DIV100Signed division
DIVU101Unsigned division
REM110Signed remainder
REMU111Unsigned remainder

State Machine — IDLE → CALC → DONE → IDLE

  • IDLE: Waits for start. Asserts busy and moves to CALC.
  • CALC: Does the computation in a single cycle, asserts done, moves to DONE.
  • DONE: Holds until start deasserts (CPU acknowledged), then returns to IDLE.

This gives a 3-cycle latency for every operation regardless of actual complexity — a simplification that works for in-order pipelines where the CPU stalls on busy.

Corner Cases Handled (per RISC-V spec)

  • Divide by zero: DIV/DIVU → all-ones result; REM/REMU → returns dividend unchanged.
  • Signed overflow (INT_MIN / -1): DIV → returns dividend; REM → returns 0.

Issues Worth Noting

  • Variable declarations inside always blocks (e.g., reg signed [...] res_mulh) are SystemVerilog-only — some tools may not support it inside procedural blocks.
  • signed_A/signed_B are declared 64-bit wide but assigned from 32-bit inputs — the width is misleading.
  • Single-cycle compute works in simulation but synthesis creates a massive combinational path.
Q 02
How does start go to 0 automatically? If done becomes 1 in CALC state itself, how does the DONE state even run?

Who deasserts start?

start is driven by the control unit (your pipeline's execute stage or hazard unit), not by this module. The control unit asserts start=1 when it issues the operation and holds it high while waiting. When it sees done=1, it moves on and stops driving start high. The mul_div module does not control start at all.

Cycle-by-cycle flow

Cycle 1: state=IDLE,  start=1  → latches to CALC, busy=1
Cycle 2: state=CALC           → computes Result, done=1, latches to DONE
                                 control unit SEES done=1, deasserts start
Cycle 3: state=DONE,  start=0 → immediately latches back to IDLE, done=0

So yes — by the time the FSM enters DONE state, start is already 0 because the control unit reacted to done=1 in the previous cycle. The DONE state does run, but for exactly one cycle, and immediately returns to IDLE.

So why does DONE state exist?

  • Clean done deassertion: done is a registered signal. Without DONE state, going CALC→IDLE directly works, but DONE makes it explicit and controlled.
  • Safety net: If the control unit is slow to deassert start (takes an extra cycle), the FSM parks in DONE and waits rather than incorrectly re-triggering a new computation.

The implicit contract

Control unit              mul_div FSM
-----------               -----------
assert start=1     →      IDLE sees start, goes to CALC
wait on busy/done  ←      CALC asserts done=1
deassert start=0   →      DONE sees !start, returns to IDLE
Both sides must honor this handshake. If your control unit deasserts start the same cycle it sees done, everything works in 3 cycles total.
Q 03
What is the point of ALUOut ← 0 + U_imm for LUI? Can't we directly store the immediate?

You're right — it's purely a hardware reuse trick

There is no architectural reason. The ALU is the only path that leads to the result register (ALUOut → Reg[rd]). There is no separate bypass wire from the immediate generator directly to the writeback stage.

So the datapath is forced to be:

imm_gen → [ALU input B]
               ↓
         ALU (0 + imm)
               ↓
            ALUOut
               ↓
            Reg[rd]

What it would take to skip the ALU

You'd need a dedicated mux at writeback:

// Extra mux needed
Reg[rd] ← (is_lui) ? U_imm : ALUOut;

That adds hardware just for one instruction. Instead, feeding 0 into ALU input A costs nothing — you already have a 0 source available on ALUSrcA (the 2'b10 case in your control unit), and the ADD result is just imm itself.

Short answer: The ALU is the only road to Reg[rd]. Adding 0 is just the toll you pay to use that road.
Q 04
Instead of creating md_op using funct3, is using funct3 directly an optimization?

Yes, exactly

The M-extension funct3 encoding is already:

000 = MUL
001 = MULH
010 = MULHSU
011 = MULHU
100 = DIV
101 = DIVU
110 = REM
111 = REMU

So you just wire IR[14:12] directly to md_op. No translation logic needed. The localparams in the module simply give readable names to what are already the correct bit patterns from the instruction encoding.

If the encodings were different from the funct3 values, you would need a decoder in between that maps one encoding to another. Here, the ISA designers made them match perfectly so that wiring is sufficient.

Q 05
What is the accumulator?

Connecting to the textbook diagram

In the shift-and-add algorithm from your YouTube video, the columns were:

M    C    A       Q        Q0
1011      0000    1101     (0) ← initialization
           ↑       ↑
    upper half   lower half (multiplier)
  • M = multiplicand (1011 = 11)
  • Q = multiplier (1101 = 13), also becomes lower half of product
  • A = upper register, starts at 0000, accumulates partial products
  • C = carry bit

In the textbook, A and Q together form a 64-bit shift register holding the growing product. That pair {A, Q} is exactly what the code calls accumulator:

accumulator[63:32]  =  A  (upper half — partial product)
accumulator[31:0]   =  Q  (lower half — in textbook, starts as multiplier)

Each cycle

  • If Q's LSB (i.e., mplier[0]) = 1: add M to upper half (A = A + M)
  • Shift the whole {C, A, Q} right by 1

After 32 shifts, the full 64-bit product is in {A, Q} = accumulator.

Q 06
The trial_sub wire — what is it, and why isn't it used?

What it does

wire [WIDTH:0] trial_sub = {remainder[WIDTH-1:0], 1'b0} - {1'b0, divisor_reg};

This wire shifts remainder left by 1 (the 1'b0 appended at the LSB) and subtracts divisor. It is a combinational preview of "what would happen if I shifted remainder and subtracted."

Why it is wrong and unused

Notice it appends 1'b0 at the LSB. But correct restoring division must shift remainder left and pull in quotient[WIDTH-1] — the MSB of the dividend register — not a hardcoded zero.

That's why S_DIV_ITER ignores this wire entirely and recomputes correctly inline:

// Correct — pulls in quotient's MSB (next dividend bit)
shifted_rem = {remainder[WIDTH-1:0], quotient[WIDTH-1]};

// Wire above was wrong — it always shifts in 0
wire trial_sub = {remainder[WIDTH-1:0], 1'b0} - ...  ← WRONG

The trial_sub wire is a leftover mistake from an earlier design iteration. It synthesizes as dead logic and does nothing.

Q 07
Why is the multiplicand added to the upper half of the accumulator? Why not lower or full?

Tracing the textbook example

M = 1011 (11),  Q = 1101 (13)
Init:    A=0000  Q=1101

Cycle 1: Q[0]=1 → A = A + M = 0000 + 1011 = 1011
         Shift right: {A,Q} = {1011,1101} >> 1 = {0101,1110}

Cycle 2: Q[0]=0 → no add
         Shift right: {0101,1110} >> 1 = {0010,1111}

Cycle 3: Q[0]=1 → A = 0010 + 1011 = 1101
         Shift right...

The positional value argument

Each bit of the multiplier Q represents a power of 2. When Q[0]=1 at iteration i, the multiplicand needs to be added at position 2^i. Since we right-shift every cycle, the upper half naturally represents the higher-order bits. Adding M to the upper half and then right-shifting is equivalent to adding M × 2^(current_bit_position).

In code:

accumulator <= ({accumulator[63:32] + mcand,   // upper half + M
                  accumulator[31:0]             // lower half unchanged
                }) >> 1;                        // then shift whole thing right
Adding to the lower half would scale the multiplicand by the wrong power of 2. Adding to the full 64-bit value would double-count the partial products already accumulated in the lower half.
Q 08
In S_MUL_ITER, do we need to write an else statement saying "continue"?

No — hardware has no concept of "continue"

if (count == WIDTH - 1)
    state <= S_FINISH;
// No else needed — if this condition is false,
// the state register is never written,
// so it retains its current value = S_MUL_ITER automatically

In an FPGA or ASIC, registers hold their value until explicitly written. Not writing = staying. The FSM loops on itself implicitly.

This is a fundamental difference from software:

SoftwareHardware (RTL)
Execution pointer moves forward; you must explicitly continue or loopEvery register keeps its value every cycle unless overwritten; "staying" is the default
Sequential — one thing at a timeParallel — all always blocks evaluate simultaneously every clock edge
Q 09
What if we use a while loop in the multiplier or division logic until count reaches WIDTH-1?

This is the most important conceptual difference between software and hardware

In software

while (count < 32) {
    // runs 32 times — sequential, fast
    count++;
}

All 32 iterations happen within one logical thread, one after another, in microseconds.

In hardware, a loop = unrolling

A while or for loop in synthesizable RTL means the synthesizer unrolls it completely into combinational logic:

// for (i=0; i<32; i++) becomes physically:
// 32 adders + 32 shifters all chained in series
// ALL evaluated in ONE clock cycle
// Critical path = 32× delay of one stage
// → Timing fails — too slow for any reasonable clock

The iterative FSM approach

Does one step per clock cycle:

Cycle 1:  one add + one shift
Cycle 2:  one add + one shift
...
Cycle 32: one add + one shift

This keeps the combinational path short (just one adder + one shifter), allowing a fast clock. You trade latency (32 cycles) for timing closure (fast clock).

This is called a multi-cycle iterative datapath and is standard practice for multiply/divide units in real CPUs — including Intel, ARM, and RISC-V cores.
Q 10
Where is accumulator[31:0] = Q ever defined? The textbook loads the multiplier into Q.

It's never set to Q — that's the key difference from the textbook

In S_IDLE initialization:

MUL: begin
    accumulator <= {WIDTH*2{1'b0}};  // entire 64 bits = ZERO
    mcand       <= A;
    mplier      <= B;                // B stored SEPARATELY, NOT in accumulator
    state       <= S_MUL_ITER;
end

Textbook vs this code

TextbookThis Code
MultiplierLoaded into Q (lower half of accumulator)Stored in separate mplier register
Accumulator{A, Q} — unified 64-bit registerProduct only, starts at zero
ShiftOne right-shift on {C, A, Q}Accumulator shifts right; mplier shifts right independently

Why does it still produce the correct result?

Both approaches are mathematically equivalent. Each cycle, mplier[0] gives the current multiplier bit (same as Q[0] in the textbook). After 32 right-shifts, the partial products pushed down from the top naturally fill accumulator[31:0] — not because Q was loaded there initially, but because 32 right-shifts pushed the partial products down into the lower half.

Q 11
Why is the upper 32 bits explicitly selected for MULH, MULHSU, MULHU? Why not lower or full?

Because of what the instruction is defined to return

32-bit × 32-bit = 64-bit result. Example:

0xFFFFFFFF × 0xFFFFFFFF
= 0xFFFFFFFE_00000001   (64 bits)
         ↑upper↑  ↑lower↑

The 64-bit result never fits in a 32-bit register. RISC-V splits it across two instructions:

MUL    rd, rs1, rs2  →  rd = lower 32 bits  (bits 31:0)
MULH   rd, rs1, rs2  →  rd = upper 32 bits  (bits 63:32)

If you want the full 64-bit product you run both instructions and combine {MULH_result, MUL_result}.

Why does the upper half matter?

  • Fixed-point multiplication (Q31 format in DSP) — the useful precision is in the upper half
  • Overflow detection — if upper half is nonzero, the result exceeded 32 bits
  • Software 64-bit multiply on 32-bit hardware
# Overflow check in assembly
mul   t0, a0, a1    # lower half
mulh  t1, a0, a1    # upper half
bnez  t1, overflow  # if upper != 0, result overflowed 32 bits

Why not full 64 bits directly?

RISC-V is a 32-bit ISA — every register is 32 bits wide. There is no 64-bit register in RV32. The architecture physically cannot return 64 bits in one instruction, hence the split into MUL + MULH.

is_upper in the code is set to 1 only for MULH, MULHSU, MULHU — exactly the instructions whose job is to return the upper half.
Q 12
What do you define as an ISA?

ISA — Instruction Set Architecture

It is the contract between software and hardware.

What it defines

  • What instructions exist — ADD, SUB, LOAD, BRANCH, etc.
  • What registers exist — how many, how wide (32 registers × 32 bits in RV32)
  • How instructions are encoded — which bits mean what (opcode, funct3, funct7...)
  • What memory model is used — how loads/stores behave
  • How exceptions/interrupts work — what happens on a fault

What it does NOT define

  • How the hardware implements it — pipelined, multi-cycle, superscalar — that's up to the designer
  • How fast it runs
  • How many cycles each instruction takes

Analogy

ISA = job description ("must be able to do ADD, LOAD, BRANCH...").
CPU = the actual employee who does the job.

Two completely different CPUs — your simple multi-cycle design and a modern Intel superscalar — can both implement the same ISA. Software compiled for that ISA runs on both, because both honor the same contract.

RISC-V ISA says:
  "ADD rd, rs1, rs2 must store rs1+rs2 into rd"

Your CPU:  does it in EXEC_R state, 4 cycles total
Intel CPU: does it in 1 cycle with deep pipelining
ARM CPU:   does it with a different internal pipeline

All three are correct implementations — the OUTPUT is what the ISA
specifies, not the internal method.
Q 13
How does Intel do ADD in 1 cycle? If ARM and Intel are not open source, how can someone like me study their architecture? Will Intel be happy or angry to hire me since I focused on their "opponent" RISC-V?

1. How does Intel do ADD in 1 cycle?

It doesn't violate anything. "1 cycle" means their pipeline stage is very short and they throw enormous hardware at it. A few techniques:

  • Deep pipelining: Intel splits execution into 15-20+ pipeline stages. Each stage does very little, so the clock can run at 5GHz. Your multi-cycle CPU has ~4 stages at maybe 50MHz. Same work, different granularity.
  • Multiple execution units: Modern Intel CPUs have 4-6 integer ALUs running in parallel. They can execute 4 ADDs simultaneously in one cycle.
  • Out-of-order execution: The CPU looks ahead 200-300 instructions, finds ones with no dependencies, and runs them in parallel even if they are not sequential in your program.
  • Micro-op translation: Modern Intel CPUs internally translate x86 instructions into micro-ops — simpler internal instructions resembling RISC. So at the deepest level, Intel is already running a RISC-like engine internally.

2. How to study Intel/ARM without open source

They publish far more than you'd think:

  • Official optimization manuals: Intel publishes full optimization manuals — thousands of pages, free at intel.com. Exact latency and throughput for every instruction.
  • ARM Architecture Reference Manuals: Full ISA spec, memory model, exception model — free at arm.com.
  • Agner Fog's manuals: A Danish professor who reverse-engineered Intel/AMD microarchitecture through careful benchmarking. Widely used in industry. Free at agner.org.
  • Academic papers: Intel and ARM engineers publish at ISCA, MICRO, HPCA. Real implementation details come through these conferences.
  • WikiChip: Community-maintained microarchitecture documentation with die shots and pipeline diagrams.
  • Patent filings: Both companies file detailed patents describing their microarchitectural innovations. Publicly searchable.

3. Will Intel care that you studied RISC-V?

They will not care at all — and here is why.

Microarchitecture concepts are universal. Pipelining, out-of-order execution, branch prediction, cache hierarchies, hazard detection — these are the same whether you implement them on x86, ARM, or RISC-V. If you deeply understand a RISC-V pipeline, you understand CPU design. The ISA is almost irrelevant to the job.

RISC-V is actually preferred for learning precisely because it is clean and unencumbered by 40 years of legacy baggage that x86 carries. Intel engineers themselves will tell you x86 is an ugly ISA to learn on.

For verification roles specifically — UVM, SystemVerilog assertions, coverage methodology, formal verification — none of that is ISA-specific. Your BlackParrot verification work is directly transferable.

The "opponent" framing — forget it entirely. Intel and ARM are competitors at the product level, not at the engineering knowledge level. RISC-V is an open standard, not a company. Intel Foundry is actively manufacturing RISC-V chips for other companies, and Intel has internal RISC-V research projects.

Knowing RISC-V deeply → you understand CPUs → Intel, AMD, ARM, Qualcomm, and Apple all want that.
Q 14
Explain S_DIV_ITER in detail — every line of the restoring division algorithm.

The Algorithm: Restoring Division in Long-Division Terms

Think of how you do long division by hand — you bring down the next digit of the dividend, try subtracting the divisor, keep the result if it fits, otherwise restore and write 0. Hardware does the exact same thing with registers.

Register Roles at the Start

quotient    = abs_A   ← dividend bits, drains out from MSB side
remainder   = 0       ← accumulates the running remainder  
divisor_reg = abs_B   ← fixed throughout the iteration
Key insight: quotient serves a dual purpose. Initially it holds the dividend bits (fed one at a time from MSB). Gradually it fills with quotient bits (inserted from LSB). The two uses share the same register but at opposite ends, passing each other over 32 cycles.

Named block declaration

begin : div_block
    reg [WIDTH:0] shifted_rem;
    reg [WIDTH:0] sub_result;

begin : div_block creates a named scope so local variables can be declared inside an always block. These are not real flip-flops — they are temporary wires used only within this combinational calculation. They are 33 bits wide (WIDTH+1) because the extra MSB acts as a sign bit after subtraction.

Step 1 — Shift remainder left, pull in next dividend bit

shifted_rem = {remainder[WIDTH-1:0], quotient[WIDTH-1]};
  • remainder[WIDTH-1:0] — drop the 33rd sign bit, take lower 32 bits
  • quotient[WIDTH-1] — the MSB of the quotient register, which is the next dividend bit
  • Concatenation shifts remainder left by 1 and brings in the next digit — exactly "bring down the next digit" from long division
Before:
remainder = 0_0000_0000   (33 bits)
quotient  = 1101_xxxx     (MSB=1 is next dividend bit)

shifted_rem = 0000_0000_1  (remainder shifted left, quotient MSB shifted in)

Step 2 — Trial subtraction

sub_result = shifted_rem - {1'b0, divisor_reg};

{1'b0, divisor_reg} zero-extends divisor to 33 bits so the sizes match. Then subtract.

The 33rd bit (MSB = bit 32) tells you the sign of the result:

  • sub_result[WIDTH] = 0 → result ≥ 0 → divisor fits → quotient bit = 1
  • sub_result[WIDTH] = 1 → result < 0 → divisor does not fit → quotient bit = 0

Step 3a — Subtraction succeeded

if (!sub_result[WIDTH]) begin
    remainder <= sub_result;
    quotient  <= {quotient[WIDTH-2:0], 1'b1};
end
  • remainder ← sub_result — keep the subtracted value (divisor fit)
  • quotient ← shift left, insert 1 at LSB — record that this bit of quotient is 1, and consume the MSB dividend bit

Step 3b — Subtraction failed, restore

end else begin
    remainder <= shifted_rem;        // discard sub_result — restore
    quotient  <= {quotient[WIDTH-2:0], 1'b0};
end
  • remainder ← shifted_rem — NOT sub_result — the subtraction is discarded and the remainder is restored to what it was before the attempt
  • quotient ← shift left, insert 0 — this quotient bit is 0

This is why the algorithm is called restoring division — when subtraction fails, you restore.

Counter and state transition

count <= count + 1;
if (count == WIDTH - 1)
    state <= S_FINISH;

After 32 iterations (count 0 to 31), every dividend bit has been consumed from the MSB side, and 32 quotient bits have been inserted from the LSB side. quotient now holds the computed quotient and remainder[WIDTH-1:0] holds the remainder.

Worked Example: 13 ÷ 3

quotient (dividend) = 0000_1101  (13)
divisor_reg         = 0000_0011  (3)
remainder           = 0_0000_0000

Iter 1: shifted_rem = {0000_0000, 0} = 0_0000_0000  (MSB of dividend = 0)
        sub         = negative → FAIL (restore)
        quotient    = 0001_1010  (shifted left, 0 inserted)

Iter 2: shifted_rem = {0000_0000, 0} → FAIL
        quotient    = 0011_0100

Iter 3: shifted_rem = {0000_0000, 0} → FAIL
        quotient    = 0110_1000

Iter 4: shifted_rem = {0000_0000, 0} → FAIL
        quotient    = 1101_0000

... (32 iterations total)

Final:
quotient  = 0000_0100  (4 = 13/3 ✓)
remainder = 0000_0001  (1 = 13%3 ✓)
Q 15
I'm very interested in how Intel calculates an instruction within 1 cycle. Where do I start to explore Intel architecture?

First — Correct the Mental Model

Intel doesn't magically do it in 1 cycle. The correct statement is: your CPU has a 4-cycle latency for ADD across the full pipeline. Intel's ADD has 1-cycle latency within the execute stage, but their full pipeline is 14–19 stages deep. The difference is pipelining + parallelism, not magic.

The Learning Ladder

Rung 1 — Pipelining (you're already here)

You already built a multi-cycle CPU. The next step is pipelining, where multiple instructions overlap stages:

Multi-cycle:   one instruction uses all stages sequentially
Pipelined:     multiple instructions overlap

Cycle:         1    2    3    4    5    6
Multi-cycle:  [  instr1 only      ][ instr2...]
Pipelined:    [F][D][E][W]
                  [F][D][E][W]
                     [F][D][E][W]

Read: Patterson & Hennessy — "Computer Organization and Design RISC-V Edition" Chapters 4–5. The single most important book for where you are now.

Rung 2 — Classic 5-stage Pipeline

Build or deeply understand a 5-stage RISC-V pipeline: IF → ID → EX → MEM → WB. Key concepts: data hazards (RAW, WAW, WAR), forwarding/bypassing, control hazards, branch prediction basics. Extend your current CPU into a 5-stage pipeline — you already have the datapath.

Rung 3 — Out-of-Order Execution (where Intel lives)

Intel's Core architecture is out-of-order superscalar. Core structures to understand:

  • ROB (Reorder Buffer) — tracks all in-flight instructions, retires them in order
  • Reservation Stations — hold instructions waiting for operands
  • Register Renaming — eliminates false WAR and WAW dependencies
  • Execution Ports — Intel has 6 ports, each runs certain operation types
  • Tomasulo's Algorithm — the foundational algorithm behind all modern OoO processors, invented at IBM in 1967, still used conceptually today

Read: Patterson & Hennessy Chapter 6 (ILP) + Hennessy & Patterson "Computer Architecture: A Quantitative Approach" Chapter 3.

Rung 4 — Intel Specifically

  • Intel Optimization Reference Manual — free at intel.com. Exact latency, throughput, execution port for every instruction.
  • Agner Fog's Microarchitecture Manual — agner.org/optimize/microarchitecture.pdf. Reverse-engineered Intel/AMD pipeline details. Most detailed unofficial documentation that exists.
  • WikiChip — en.wikichip.org/wiki/intel. Pipeline diagrams, die shots, cache hierarchies for every Intel generation.

Rung 5 — Academic Papers

Intel engineers publish at ISCA, MICRO, and HPCA every year. Search Google Scholar for "Intel microarchitecture", "Skylake pipeline MICRO", "branch prediction Intel ISCA". Free through ACM/IEEE digital libraries — your college likely has access.

Rung 6 — Simulators and Open-Source OoO

  • gem5 — industry-standard CPU simulator, configurable OoO cores. gem5.org
  • BOOM (Berkeley Out-of-Order Machine) — open-source OoO RISC-V core in Chisel. The closest thing to "Intel architecture but open source." Reading this RTL will teach you more than any textbook. github.com/riscv-boom/riscv-boom

The One Thread That Ties It All Together

Everything Intel does — pipelining, OoO, superscalar — is answering one question: How do we keep all execution units busy every cycle? Your current CPU wastes cycles. The entire evolution of CPU microarchitecture from 1980 to today is the story of progressively eliminating those wasted cycles. Follow that thread and you'll naturally arrive at understanding Intel's architecture.
