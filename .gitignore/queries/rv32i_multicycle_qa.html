01
Decode Stage
Q
Why are ALU operations present in the DECODE block? The decode block's duty is just to decode the instruction, right?
ANSWER

You're right that in a single-cycle or pipeline context, Decode just reads registers and generates control signals. But in a multi-cycle design, the DECODE state is a free clock cycle where the ALU is sitting completely idle. The FSM exploits that idle hardware to precompute things that will be needed later.

◆
Core principle: In a multi-cycle design, you have exactly one ALU shared across all stages. Any cycle where the ALU would otherwise be idle is an opportunity to precompute something that saves a future state. DECODE is always idle from the ALU's perspective.

For branches → BRANCH_EX path

SystemVerilog — DECODE state
// Non-jump path in DECODE
ALUSrcA_ctrl = 2'b00; // PC
ALUSrcB_ctrl = 2'b10; // imm
ALU_OP       = 3'd3;  // ADD → ALUOut = PC + imm (branch target)

The branch target PC + imm gets computed and saved into ALUOut at the end of DECODE. Then in BRANCH_EX, the ALU is busy doing A − B to evaluate condition flags. If the branch is taken, where does the target come from? Straight from ALUOut via PCSource_ctrl = 2'b01. If you hadn't precomputed it here, you'd need a dedicated extra state just to calculate the branch target.

For jumps JAL/JALR → JUMP_EX / JALR_EX path

SystemVerilog — DECODE state (jump path)
ALUSrcA_ctrl = 2'b00; // PC
ALUSrcB_ctrl = 2'b01; // 4
ALU_OP       = 3'd3;  // ADD → ALUOut = PC + 4 (return address)

JAL and JALR must write PC + 4 into rd as the return address. In JUMP_EX/JALR_EX, the ALU is busy computing the jump target (PC + imm or A + imm). So the return address PC + 4 is precomputed here and saved into ALUOut. The write-back in JUMP_EX then uses MemToReg = 0 which selects ALUOut — that's how rd gets PC + 4 without needing an extra adder or an extra state.

△
The DECODE precomputation isn't "for every non-jump instruction" — it specifically serves branches and AUIPC. For R-type, I-type, Load, Store, LUI — this computation happens but gets overwritten by the ALU in the next state. It's wasted work but harmless, because the FSM has no cheaper way to handle branches and AUIPC without a dedicated extra state.
02
PC Arithmetic
Q
For every operation except jump type, does PC get added with imm? Are there no cases where PC = PC + 4? Tell me in which operations PC is added with immediate and in which cases added with 4.
ANSWER

PC = PC + imm (PC actually jumps)

InstructionWhy
JALUnconditional jump by offset from PC
Branch (taken)Condition passed — jumps to PC + offset

That's it. Only 2 cases where PC itself moves by an immediate.

PC = PC + 4 (normal sequential flow)

InstructionWhy
R-typePure register arithmetic, no jump
I-type arithmeticSame — result goes to rd, PC moves forward
Load (LW)Loads a value, PC still sequential
Store (SW)Writes memory, PC still sequential
Branch (not taken)Condition failed — just move on
LUIJust writes a constant to rd
AUIPCrd = PC + imm, but PC itself still goes +4
JALRPC = (rs1 + imm) & ~1, not PC + imm

Now look at your DECODE block again

SystemVerilog
// Non-jump path
ALUSrcA_ctrl = 2'b00; // PC
ALUSrcB_ctrl = 2'b10; // imm  ← PC + imm into ALUOut

This precomputed ALUOut = PC + imm is only actually consumed by two cases:

  • BRANCH_EX — uses ALUOut as the branch target if taken
  • AUIPC_EX — uses ALUOut as the value written to rd

For R-type, I-type, Load, Store, LUI — this computation happens but gets overwritten by the ALU in the next state. It's wasted work but harmless, because the FSM has no cheaper way to handle branches and AUIPC without a dedicated extra state.

03
branch_taken Signal
Q
How is branch_taken enabled? Who turns it to 1?
ANSWER

Nobody in the control unit. Look at the top module — branch_taken is a combinational block in the datapath, computed from ALU flags:

SystemVerilog — rv32i_multi_cycle.sv (top module)
reg branch_taken;
always @(*) begin
    case(funct3)
        3'b000 : branch_taken = zero_flag;            // BEQ
        3'b001 : branch_taken = ~zero_flag;           // BNE
        3'b100 : branch_taken = negative ^ overflow;  // BLT
        3'b101 : branch_taken = ~(negative ^ overflow);// BGE
        3'b110 : branch_taken = ~carry_out;           // BLTU
        3'b111 : branch_taken = carry_out;            // BGEU
        default: branch_taken = 0;
    endcase
end

This wire then goes into the control unit as an input (input branch_taken). The FSM doesn't set it — it just reads it. The flow is:

BRANCH_EX state sets ALUSrcA=A, ALUSrcB=B, ALU_OP=SUB → ALU computes A−B → produces zero_flag / negative / overflow → branch_taken logic evaluates combinationally → FSM reads branch_taken to decide next_state
04
Memory States
Q
Why are there so many memory states — MEM_ADDR, MEM_READ, MEM_WB, MEM_WRITE? What is each one for?
ANSWER

Because a load (LW) and a store (SW) are genuinely different operations that share an address calculation step but diverge after it. The state machine splits them cleanly:

MEM_ADDR → computes ALUOut = A + imm (effective address) | ┌──────┴──────┐ LW SW ↓ ↓ MEM_READ MEM_WRITE (MemRead=1) (MemWrite=1 → done, go to PC_INC) ↓ MEM_WB (RegWrite=1, write MDR into rd) (also does PC+4 concurrently here!)
StateWhat it doesKey signals
MEM_ADDR ALU computes A + imm. Result saved in ALUOut. Used by both LW and SW. ALUSrcA=A, ALUSrcB=imm, ALU_OP=ADD
MEM_READ Asserts MemRead=1. Memory reads from ALUOut address and puts data into MDR at the next clock edge. MemRead=1
MEM_WB Asserts RegWrite=1, MemToReg=1 — writes MDR into destination register. Also does PC+4 concurrently. RegWrite=1, MemToReg=1, PCWrite=1
MEM_WRITE Asserts MemWrite=1. Writes read_data2 to memory at the ALUOut address. Done in one state, goes straight to PC_INC. MemWrite=1

Why are MEM_READ and MEM_WB two separate states for loads? Memory can't read and write-back in the same cycle. The read happens in MEM_READ, latches into MDR at the clock edge, then MEM_WB reads from MDR. Stores don't need this second step — once the address is in ALUOut and MemWrite=1, the store completes in one cycle.

Why does MEM_WB also do PC+4? This is the concurrent PC increment optimization — the ALU is free during write-back, so the FSM uses it to compute PC+4 at the same time, saving one full state cycle.

05
ALUOut vs alu_result
Q
ALUOut and alu_result — are these different things? How does a single ALU produce two different outputs? How does ALUOut get its value assigned in the DECODE stage?
ANSWER

There is one physical ALU, one output wire called alu_result. ALUOut is a register (flip-flop) that captures alu_result at the clock edge. Think of it as memory for the ALU's previous result.

[ALU] ──── alu_result (combinational wire, changes every cycle) │ [ALUOut reg] ──── ALUOut (holds alu_result from PREVIOUS cycle)

Why this matters — across two cycles for branches

Cycle (DECODE): ALU computes PC + imm → alu_result = 0x104 Clock edge: ALUOut ← 0x104 Cycle (BRANCH_EX): ALU now computes A − B → alu_result = 0x000 (for flags) ALUOut still holds 0x104 from last cycle If branch taken: PCSource_ctrl = 2'b01 → PC = ALUOut = 0x104 ✓

The ALU did two different things in two consecutive cycles. ALUOut preserved the first result while the ALU was busy doing the second computation. That is the entire point of the state registers.

How does ALUOut get assigned?

It is supposed to be updated every clock cycle with ALUOut <= alu_result, making it a one-cycle-delayed version of alu_result. However — look at your current top module:

SystemVerilog — rv32i_multi_cycle.sv (current state)
always @(posedge clk) begin
    if (!rst_n) begin
        IR     <= 32'b0; MDR <= 32'b0;
        A      <= 32'b0; B   <= 32'b0; ALUOut <= 32'b0;
    end else begin
        if (IRWrite) IR <= mem_instr;
        // MDR    <= mem_data;    ← COMMENTED OUT
        // A      <= read_data1;  ← COMMENTED OUT
        // B      <= read_data2;  ← COMMENTED OUT
        // ALUOut <= alu_result;  ← COMMENTED OUT  ← BUG
    end
end
✕
Active bug in current code: ALUOut, MDR, A, and B are never actually updated — they stay 0 forever. The write-back assign write_data = (MemToReg)? MDR : ALUOut is reading stale zeros. Uncommenting these four lines is the immediate next step to wire up.
06
Same-Cycle branch_taken
Q
In the current cycle, the control unit has BRANCH_EX as the current state. It sends the ALU to check subtraction. But how does it also read branch_taken in the same state — the ALU hasn't finished yet when the if (branch_taken) check happens, right?
ANSWER

This is the most important digital design concept to internalize. The answer is: combinational logic has no concept of "same state" time — it all settles instantly.

What is clocked vs what is combinational

concept
CLOCKED (only these wait for clock edge):
  current_state   ← next_state
  PC              ← PC_next      (if PCWrite)
  ALUOut          ← alu_result
  A, B, MDR, IR   ← their inputs

COMBINATIONAL (no clock, settles in nanoseconds):
  control unit output logic   always @(*)
  ALU computation             pure gates
  branch_taken logic          always @(*)

Within one clock cycle, this entire chain resolves simultaneously, like dominoes:

current_state = BRANCH_EX (stable register value) │ ▼ control unit always@(*) fires → outputs ALUSrcA=A, ALUSrcB=B, ALU_OP=SUB │ ▼ ALU combinationally computes A−B → produces zero_flag, negative, overflow │ ▼ branch_taken always@(*) fires → evaluates e.g. zero_flag for BEQ │ ▼ control unit always@(*) fires AGAIN (branch_taken is in its sensitivity list) → now sets PCWrite=1, PCSource_ctrl=2'b01 │ ▼ clock edge arrives → PC latches PC_next, state latches next_state

The always @(*) in your control unit re-evaluates every time any input changes, including branch_taken. So the simulator sees:

  • First pass: branch_taken is whatever it was → control unit settles partially
  • branch_taken changes because ALU flags changed → control unit re-evaluates
  • Everything settles to final stable values
  • Clock edge arrives and latches the final stable values
◆
There is no contradiction. The if (branch_taken) inside BRANCH_EX is not an if-statement executing over time — it is hardware wiring. It permanently connects branch_taken to the enable of PCWrite. When branch_taken is 1, PCWrite is 1. When it's 0, PCWrite is 0. All within the same cycle, all before the clock edge.
07
SVT Golden Model
Q
The SVT plan hardcodes expected register values for a specific program. How can I use different instructions and either feed expected results manually, or automatically generate them so I don't have to recalculate by hand every time I change the program?
ANSWER

The hardcoded SVT is essentially a snapshot test — it breaks the moment you touch instruction_mem.v. The right fix is a Python golden model that reads the same memory file your RTL uses and auto-generates expected values.

instruction_mem.v │ ├──→ RTL (Verilator/iverilog) ──→ actual register dump │ └──→ Python ISS ─────────────→ expected register dump │ ▼ auto-generate expected_regs.hex

Approach 1 — Self-Checking Program (simplest)

Instead of the testbench checking register values, the program itself checks its own results and writes a pass/fail to a magic memory address. Your testbench only watches that address. This is exactly the bp_finish(0/1) pattern from BlackParrot.

Assembly concept
addi x1, x0, 5
addi x2, x0, 3
add  x3, x1, x2        # x3 should be 8

addi x4, x0, 8         # load expected value
beq  x3, x4, PASS      # if correct, jump to pass
FAIL:
  sw x0, 0(x0)         # write 0 to mem[0] = FAIL signal
  j END
PASS:
  addi x5, x0, 1
  sw x5, 0(x0)         # write 1 to mem[0] = PASS signal
END:
Verilog testbench — only checks one address
initial begin
  #2000;
  if (dut.dm.mem[0] == 32'd1)
    $display("[SVT PASS]");
  else
    $display("[SVT FAIL] mem[0] = %0d", dut.dm.mem[0]);
end

Approach 2 — Python Golden Model (best for your use case)

Write a tiny Python RV32I simulator that reads the same instruction_mem.v your RTL uses, simulates it, and auto-generates the expected values. The Makefile runs Python before every simulation so expected values are always in sync.

Python — golden_model.py (key structure)
def simulate(instrs, steps=200):
    regs = [0] * 32
    mem  = {}
    pc   = 0

    for _ in range(steps):
        instr  = instrs[pc >> 2]
        opcode = instr & 0x7F
        # ... decode fields ...

        if opcode == 0x33:   # R-type: ADD, SUB, AND, OR ...
            regs[rd] = (r1 + r2) & 0xFFFFFFFF
        elif opcode == 0x13: # I-type: ADDI, XORI ...
            regs[rd] = (r1 + i_imm) & 0xFFFFFFFF
        # ... all other opcodes ...

    return regs, mem, pc

# Emit .hex files for $readmemh in testbench
with open("expected_regs.hex", 'w') as f:
    for v in regs:
        f.write(f"{v:08x}\n")
Makefile — auto-regenerates golden before every sim
svt: expected_regs.hex svt_sim
	./svt_sim

expected_regs.hex: src/instruction_mem.v
	python3 golden_model.py    # runs only when imem changes

svt_sim: tb/svt_tb.v src/*.v
	iverilog -o svt_sim tb/svt_tb.v src/*.v

Now when you change instruction_mem.v, make svt automatically regenerates expected values before running the testbench. No manual update ever needed.

08
Regression Suite
Q
I want per-instruction regression tests in a tests/ directory (add_test, sub_test, branch_test etc.) that I can run all at once and get pass/fail output per test. I have a golden model Python file. How do I feed each test its own instructions and expected values?
ANSWER

The key architectural shift is: right now your instruction memory is hardcoded in instruction_mem.v. For regression tests to work, the memory must be loadable from a file at runtime so each test can inject its own program. Everything else follows from that.

Full directory structure

shell
tests/
  add_test/
    program.hex           ← you write this (raw hex instructions)
    expected_regs.hex     ← auto-generated by golden_model.py
    expected_mem.hex      ← auto-generated
    expected_pc.hex       ← auto-generated
  sub_test/
    program.hex
  branch_test/
    program.hex
  ...

src/
  instruction_mem.v       ← modify once to use $readmemh

tb/
  svt_tb.v               ← uses +plusarg to know which test to run

golden_model.py           ← takes test dir as argument
Makefile                  ← new regression target

Step 1 — Modify instruction_mem.v to load from file

Verilog
module instruction_memory #(
    parameter MEM_FILE = "tests/add_test/program.hex"
)(
    input  [31:0] addr,
    output [31:0] instr
);
    reg [31:0] mem [0:255];

    initial begin
        $readmemh(MEM_FILE, mem);
    end

    assign instr = mem[addr >> 2];
endmodule

Step 2 — Write each test as a program.hex

tests/add_test/program.hex
# addi x1, x0, 5
00500093
# addi x2, x0, 3
00300113
# add  x3, x1, x2
002081b3
# sw x3, 0(x0) — write result to mem[0]
00302023

Step 3 — Run golden_model.py per test

Shell
python3 golden_model.py tests/add_test
python3 golden_model.py tests/branch_test
# generates expected_regs.hex, expected_mem.hex, expected_pc.hex in each dir

Step 4 — Testbench uses +plusargs to select test

Verilog — tb/svt_tb.v
initial begin
    // Get test name: +TEST=add_test
    if (!$value$plusargs("TEST=%s", test_name))
        test_name = "add_test";

    $sformat(regs_file, "tests/%0s/expected_regs.hex", test_name);
    $readmemh(regs_file, expected_regs);
    $readmemh(prog_file, dut.imem.mem); // inject program into DUT

    rst_n = 0; repeat(4) @(posedge clk); rst_n = 1;
    #2000;

    // compare all 32 regs, PC, data memory ...
    if (mismatches == 0)
        $display("[SVT PASS] %0s", test_name);
    else
        $display("[SVT FAIL] %0s  (%0d mismatches)", test_name, mismatches);
end

Step 5 — Makefile regression target

Makefile
TESTS = add_test sub_test and_test branch_test jal_test lw_sw_test

regression: svt_sim golden
	@echo "=============================="
	@echo "   RV32I Regression Suite     "
	@echo "=============================="
	@for t in $(TESTS); do \
	    ./svt_sim +TEST=$$t 2>&1 | grep -E "SVT|MISMATCH"; \
	done
	@echo "=============================="

golden:
	@for t in $(TESTS); do \
	    python3 golden_model.py tests/$$t; \
	done

# Run a single test during development
test_%: svt_sim
	python3 golden_model.py tests/$*
	./svt_sim +TEST=$*
